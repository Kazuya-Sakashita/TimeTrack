# Skill: API 設計 (OpenAPI)

新しい API を設計・追加するときの進め方。

## いつ使うか

- 新しいエンドポイントが必要なとき
- 既存 API の仕様を変えたいとき

## 判断基準

- その API は本当に必要か？ 既存で代替できないか。
- 粒度は適切か（1 エンドポイント = 1 目的）。
- 認証・認可の要件は明確か。
- ID は public_id を使っているか。

## 進め方

1. `openapi/openapi.yaml` に定義を追加（なければ作成方針を確認）。
2. パス / メソッド / リクエスト / レスポンス / ステータス / エラーを記述。
3. 共通スキーマは `components/schemas` にまとめる。
4. 認証が必要なら `security` を明記。
5. 実装前にこの仕様をレビューする。

## チェックリスト

- [ ] パスの ID は public_id（連番でない）
- [ ] リクエスト / レスポンスのスキーマが定義済み
- [ ] ステータスコード（200/201/400/401/403/404/422）が適切
- [ ] エラー形式が共通フォーマットに従う
- [ ] 認可要件（誰がアクセスできるか）が明記されている
- [ ] 破壊的変更になっていない（必要なら新規追加）

## やってはいけない

- OpenAPI を飛ばして実装に進む
- 仕様にないフィールドを追加する
