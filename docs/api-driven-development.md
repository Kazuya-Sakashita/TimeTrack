# API 駆動開発 (API-Driven Development)

## 考え方

API の「契約（入力・出力・エラー）」を **実装より先に** 確定させる開発手法。
TimeTrack では OpenAPI (`openapi/openapi.yaml`) を唯一の仕様書とする。

### なぜ採用するか（設計意図）

- フロントとバックが同じ契約を見て独立に開発できる
- モック / 型生成 / テストを仕様から導ける
- 仕様変更の影響を一箇所で管理できる
- 設計判断が記事のネタになる

## 開発フロー

```
1. OpenAPI にエンドポイントを定義
   - パス / メソッド / リクエスト / レスポンス / ステータス / エラー
2. 仕様レビュー（命名・粒度・public_id・認可要件）
3. Rails 実装（Controller は薄く、ロジックは Model/Service）
4. Request Spec で契約を検証
5. Next.js 実装（仕様の型を使う）
6. E2E / 動作確認
```

## OpenAPI 記述ルール

- パスの ID は **public_id**（例: `/attendances/{public_id}`）。
- 共通スキーマは `components/schemas` にまとめ重複を避ける。
- エラーレスポンスの形式を統一する（例: `{ "error": { "code", "message" } }`）。
- 認証が必要なエンドポイントは `security` を明記する。
- ステータスコードを正しく定義する（200/201/400/401/403/404/422 等）。

## 仕様とコードがずれたとき

**OpenAPI を正** とし、コードを直す。
仕様を変えたいときは、まず OpenAPI を更新し、レビューしてから実装する。

## やってはいけないこと

- OpenAPI 未定義の API を実装する
- 仕様にないフィールドを勝手に返す
- 既存エンドポイントの形を黙って変える（破壊的変更は新規追加で回避）
