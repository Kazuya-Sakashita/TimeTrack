# テスト方針

## 主軸は Request Spec

API 駆動開発では「API の契約が守られているか」が最重要。
そのため **Request Spec を主軸** に据える。

### Request Spec で見ること

- 正しいリクエストで期待するステータス・レスポンスが返るか
- 認証なし → 401、権限なし → 403
- バリデーション失敗 → 422
- レスポンスの形が OpenAPI と一致するか（契約テスト）
- public_id が返り、内部 id が漏れていないか

## テストの種類

| 種類 | 目的 |
|------|------|
| Request Spec | API の入出力・ステータス・認可（主軸） |
| Model Spec | バリデーション・スコープ・ビジネスロジック |
| Policy Spec | ロールごとのアクセス可否 |
| Frontend Component/Integration | 画面の挙動（実装フェーズで方針確定） |

## 書き方の指針

- 1 つの spec は 1 つの振る舞いを検証する。
- 正常系だけでなく **異常系・権限系** を必ず書く。
- テストデータは factory（FactoryBot 想定）で用意する。
- 「ログイン中の従業員」「管理者」など状態ごとに分けて検証する。

## 完了の定義（Definition of Done）

API 実装は、次が揃って初めて「完了」とする。

1. OpenAPI に定義がある
2. Rails 実装がある
3. Request Spec が通る（正常 + 異常 + 認可）
4. 内部 id が漏れていない

> テストなしの API を「完了」と報告しないこと。
